# [T122] Remove the AeroSpace resize binding mode; resize goes modeless

**Phase:** Phase 7: Claude Code ergonomics
**Status:** `done`
**Owner:** —
**BlockedBy:** —
**Validation:** `./test.sh` 33/33; `aerospace.toml` parsed with `tomllib` (no test covers toml syntax); `aerospace reload-config --dry-run --warnings-as-errors` against the live symlink after landing

## Goal

Stop `⌥R` from presenting as a frozen keyboard.

## Acceptance Criteria

- [x] `alt-r = 'mode resize'` removed from `[mode.main.binding]`
- [x] `[mode.resize.binding]` block removed entirely
- [x] `balance-sizes`, the mode's only binding without a modeless equivalent, promoted to `alt-b`
- [x] `[mode.service.binding]` left untouched
- [x] Cheatsheet loses the Resize mode section, gains `⌥B` under Layout
- [x] Column alignment still passes after the cheatsheet edit
- [x] TOML parses and the remaining modes are exactly `main` and `service`

## Context

Reported as "struggling with Option+R and Option+F". Option+F turned out to be working as configured (`fullscreen`, AeroSpace's own, not macOS green-button), and the real complaint behind it was two Brave windows that would not tile side by side: one was `layout=floating` and workspace 5's root was `v_tiles`. The float almost certainly came from a slipped Shift, since `alt-shift-f` (float toggle) sits one key from `alt-f` (fullscreen).

Option+R was a genuine defect. It is a mode switch, not an action, and with `on-mode-changed = []` it announced nothing. Inside the mode only `h/j/k/l/b/↩/esc` were bound and every other keystroke was swallowed with no echo and no indicator, which is exactly what a hung keyboard or a dropped Voyager connection looks like.

## Decisions

### 2026-08-16 — Delete the mode rather than add an indicator

The mode's only capability beyond the existing `alt-i`/`alt-o` bindings was explicit width-vs-height control. `resize smart` already picks the axis from the parent container's orientation, and `⌥/` flips the container when the other axis is wanted, so the mode was trading a rarely-needed axis override against a keyboard that appears to hang. Deleting it also removes the shared-state problem below.

Consequence accepted: no strict cross-axis resize. Reintroduce `resize width`/`resize height` on a modeless binding if it bites.

### 2026-08-16 — Rejected: JankyBorders colour as a mode indicator

The first fix attempted was `on-mode-changed` driving `borders` to recolour while in resize mode. Three problems, in order of severity:

`borders` is a single process updated by re-invocation (`man borders`: "If an instance of borders is already running, subsequent invocations will update the existing process"). An indicator therefore has to hard-code the colour it restores on exit.

That restore would have silently ended an open audition. ADR-033/T117 recorded the border colour as "still being auditioned", and it still is: the live instance (PID 40195, started 12:54 on 15 Aug — roughly four hours after AeroSpace at 09:07, so not from `after-startup-command`, and reparented to launchd as `exec-and-forget` does) runs Macchiato `0xffe1e3e4`/`0xff494d64` at `width=6.0`, while the toml declares Mocha `0xffa6adc8`/`0xff313244` at `8.0`. `git log -L13,13` confirms the toml line never changed, so the divergence is the audition, not drift to repair.

`$AEROSPACE_MODE` is not reliably exported to the callback in 0.21.3-Beta, so the branch would have needed one binding per mode anyway.

Also rejected: `osascript` notification banners (one per mode switch), and keeping the mode with better docs (the cheatsheet already documented `esc`, and the trap still fired).

### 2026-08-16 — Border-colour drift left alone

Not repaired here. It is the open decision from ADR-033, and picking a winner is the user's call, not a side effect of a keybinding fix.
