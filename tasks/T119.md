# [T119] Stop the per-session permission prompts when working in dotfiles

**Phase:** Phase 7: Claude Code ergonomics
**Status:** `done`
**Owner:** —
**BlockedBy:** —
**Validation:** `jq -e . .claude/settings.json` exits 0; all 20 macOS destinations in `links.map` match an `Edit(...)` allow rule; `./test.sh` 22/22

## Goal

Open Claude Code in `~/dotfiles` and edit the things this repo manages without a permission prompt each session, without loosening permissions for every other project.

## Acceptance Criteria

- [x] New `.claude/settings.json` at the repo root (project scope)
- [x] Every macOS destination in `links.map` covered by an `Edit(...)` allow rule
- [x] The generated per-machine files (`~/.editor_env`, `~/.gitconfig.local`, `~/.zshrc.local`) covered too
- [x] `permissions.additionalDirectories` brings the out-of-repo config roots into scope
- [x] Nothing added to the user-scope `config/claude/settings.json`, so the grants do not follow the agent into other projects
- [x] `~/.claude` grants enumerated file by file, never `~/.claude/**`
- [x] `worktree.bgIsolation: "none"` so background sessions can edit this repo in place
- [ ] `git add .claude/settings.json` — `.claude/` has never been tracked here, so the file is machine-local until it is

## Context

The repo's whole job is writing files that live outside itself: `links.map` has 20 macOS destinations, all under `$HOME` and none inside `~/dotfiles`. Claude Code treats each of those as out of scope, so a session that touches them prompts, and the grant dies with the session, so the same prompts return the next morning.

The prompts had been accumulating in `.claude/settings.local.json` (untracked, ~80 entries, mostly one-off `Bash(...)` strings from individual approvals). That file is machine-local scratch: not reviewed, not shared, not portable to the Windows machine. The durable answer is a project settings file that states the grants deliberately.

Before this change the repo had `Read` rules but no `Edit` or `Write` rule anywhere, which is why reads were silent and every write prompted.

## Decisions

### 2026-08-15 — Project scope, not user scope

The rules go in `~/dotfiles/.claude/settings.json`, not in `config/claude/settings.json` (which is symlinked to `~/.claude/settings.json` and therefore applies everywhere).

Allowing `Edit(~/.zshrc)` at user scope would mean any Claude Code session, in any project, could rewrite the shell rc without asking, directly contradicting `CLAUDE.md`'s "no edits to shell rc outside the dotfiles flow". Project scope makes the grant conditional on the cwd being this repo, which is exactly the exception `CLAUDE.md` already carves out.

### 2026-08-15 — Enumerate `~/.claude`, do not wildcard it

`~/.warp/**` and `~/.codex/**` are fine as wildcards: those trees are entirely dotfiles-managed. `~/.claude` is not, since it also holds `history.jsonl`, `sessions/`, `projects/`, `daemon.log` and the telemetry cache. The four managed entries (`settings.json`, `statusline.sh`, `hooks`, `skills`) are listed individually so the grant cannot reach session history.

The two directory symlinks need both forms: `Edit(~/.claude/hooks)` for the symlink node itself and `Edit(~/.claude/hooks/**)` for its contents.

### 2026-08-15 — Tilde paths in rules, absolute in `additionalDirectories`

Claude Code's settings documentation uses `Read(~/.zshrc)` in its own example, so `~/` is the supported spelling for file-tool rules and keeps the file portable. `additionalDirectories` is only ever documented with absolute paths, so those five entries are spelled out in full rather than guessed at.

### 2026-08-15 — `bgIsolation: "none"` for this repo

Background Claude Code sessions refuse to edit a repo's live checkout until they create a git worktree. That default is wrong here twice over: an edit inside a worktree copy is not symlinked into `$HOME`, so it does nothing, and worktrees branch from `origin/main`, which routinely lacks the uncommitted work in this checkout, so doc edits on a branch conflict on merge. This repo's convention is edit in place then `/ship`, not branch per change. The key is read at session start, so it takes effect from the next session.

### 2026-08-15 — `settings.local.json` left alone

T101 pruned it from 73 lines to 22; it has drifted back to roughly 80. Pruning is worth doing but is a separate pass. Deleting entries that are currently suppressing prompts, in a task whose entire point is removing prompts, is the wrong order.

## Notes

`~/Library/Application Support/obsidian/obsidian.json` is the one managed destination inside another application's data container. The `Edit(...)` rule handles Claude Code's prompt for it.

The macOS consent dialog, "«Ghostty» would like to access data from other apps", is a different mechanism: TCC (`kTCCServiceSystemPolicyAppData`), granted per terminal application in System Settings, Privacy & Security, Files and Folders. No file in this repo affects it.
